# agent-hive

## v6: リーダー1体+サブスレッド実行(壁打ち→計画→並行作業)

構造を再編した。**メインチャットにはリーダー1体だけ**が常駐し、ユーザーはそこで壁打ちしながら計画を固める。リーダーは計画を project 付きタスクに起票し、`open_thread {project, goal}` で**サブスレッドを開く**——スレッドごとに専用ボードと専用worktreeを持つ3ワーカー(アルファ=設計・実装/ベータ=検証・レビュー/ガンマ=進行・調整)が立ち上がり、並行作業する。

- **メインチャット**(タブ「メイン(壁打ち)」): リーダーと1:1。曖昧さを潰し、計画を固め、タスク起票(project必須)とopen_threadで実行に移す
- **サブスレッド**(タブがスレッドごとに増える): 専用ボードのストリーム+3ワーカーのカード+そのprojectのタスクだけが見える。入力欄はそのスレッドのワーカー全員に届く
- **混線の構造的防止**: ワーカーは `claim_next_task {project: 自スレッド}` でしか請求しない(personaに明記+キックオフで指示)。他スレッドのボード投稿で起床しない(ChatHostがthreadタグで遮断)。spawnされた子も自分のスレッドのボードに流れる
- ワーカーidは `<スレッド名>-<ワーカー名>`(例: cuda-compress-alpha)。worktree/ブランチ/タスク請求ファイルもこれで分離されるので、複数スレッドを同時に開いても干渉しない

複数エージェントが**同一ワークスペースで同時に作業**し、**共有ボードで横につながり**ながらコーディングするハーネス。単一エージェントでは起きない「見逃し」を、実装→レビュー→修正→独立再検証の複数視点で拾うために作る。

最終更新: 2026-09-25。現況: v5実装済み(メインチャット常駐+スポーン階層+横断面ボード+継続ラウンド/worktree後始末)。デスクトップは既定でchat mode。テスト31件通過。実測: 4エージェントのシナリオ完走が**$0.0056**、chat modeで「指示→スポーン→並列実装→マージ→発見器レビュー」の循環を実走確認。

## v5: メインチャット+階層スポーン(横つながり優先)

構造: ユーザーは**メインチャット**(メイン3体が常駐)に指示を送る。メインは指示をタスク単位に分解し、`spawn_agent`でサブを立てる。サブも`spawn_agent`で並列作業員を立てられる(深さ上限`hierarchy.maxDepth=2`、同時`maxConcurrent=6`)。

**階層は仕事の組織化だけに使い、コミュニケーションは全部横**:

- 報告は必ずボード(親への秘密チャネルは物理的に存在しない)。全レベルが同じ1本のボードを購読
- スポーン時に渡すのは**初期ブリーフ1回きり**。以後の指示はボード経由(全員に見える)
- `create_task`/`spawn_agent`はレベル無関係で全員が使える(作業員がレビューを起票する等の横の働きかけが起きる)
- スポーンされたエージェントにはブリーフが**請求済みタスク**として割り当てられ、finish_taskでmainへ自動マージされる(成果の取りこぼしを構造が防ぐ)
- メインのラウンド終了時にも作業を自動マージ(ラウンド=有限ターンの応答、記憶は次ラウンドへ続く)

動かし方: `npm run chat`(= `node src/index.js --chat`)→ UIの入力欄から指示。ユーザー入力は全メインを時間差で起こし(同時だと議論にならないため)、ボードの`@表示名`で特定のメインを呼べる。メインの役割: アルファ=設計・実装統括/ベータ=検証・レビュー統括/ガンマ=進行・調整。

### スポーン済みエージェントの後始末(v5.1)

- **ターン上限で中断したスポーン済みエージェントは、同じworktree・同じ記憶で1回だけ自動継続**する
- 終了後、未コミット/未マージがゼロならworktreeとブランチを自動掃除。作業が残っているなら**worktreeを保持**し、ボードに「`worktrees/<id>` に未反映の作業あり」と告知する(他のエージェントやあなたが引き継ぎを判断できる)

## コスト削減(v4.5・AIの扱いはZCode準拠)

設計はZCode OSS(`apps/zcode-cli/packages/core/src/compact/`)の移植が基本。Codex/OpenCodeは参考調査元。

| 仕組み | 内容 | 出典 |
|---|---|---|
| **usage計測** | OpenRouterの`usage`(prompt/completion/**reasoning_tokens**/**cost実費**)を全呼び出しで収集。エージェント別累積をUI表示+終了サマリ出力 | ZCode provider usage優先方式 |
| **microcompact** | 直近5件のツール結果だけ残し、古いものはプレースホルダに置換。**LLM呼び出しなし**。発火は文脈推定が窓の90%超えたとき、最低削減256トークン | ZCode microcompact.ts(定数ごと移植) |
| **autocompact** | provider usage(優先)/推定が「窓−出力予約(21Kキャップ)」の90%超えたら、モデルに構造化要約させて履歴を `[system, 要約, 直近4件]` に置換。連続3回失敗でサーキットブレーク | ZCode compact/policy.ts+prompt.ts |
| **idle強制終了** | claim_next_taskの連続3回失敗を**エンジンが数えて**打ち切り(待ち専用エージェントの無駄呼び出しとウォールタイムを削る) | hive固有(v3実走の教訓) |
| **reasoning_effort** | `model.reasoningEffort: "low"`をリクエストに付与(思考トークンは課金対象) | Codexのmodel_reasoning_effort |
| **エージェント別モデル** | `agents[].model` / `agents[].reasoningEffort`で上書き可 | OpenCodeのマルチモデル流 |
| **予算ブレーキ** | `budget.maxTokensPerRun`超過でグレースフル停止(ボードに予算停止を告知)。**判定はこのラン(ループ実行)単位**(v5.4)——常駐chatのセッション累積で判定すると使い切り時にチャット全体が応答不能になるため | discord-agentsのbudget文化 |

実測(2026-09-25, stringutilシナリオ): **39呼び出し / prompt 100,246 / completion 1,764 / 思考175 / $0.0056**。`reasoningEffort: low`により思考トークンはほぼゼロ化。短いシナリオではmicrocompact/autocompactは不発(発火条件はユニットテストで検証済み、長時間ランの保険)。

### autocompactの読み取り時キュレーション(v5.2)

要約は「現在遂行中のタスクが判明した状態」で行う(JIT memory, arXiv:2609.27334の読み取り時キュレーション)。圧縮時に請求中タスクの本文(無ければ直近のユーザー指示)を要約条件へ渡し、**遂行に不要な細部は捨ててよく、必要な要素(対象ファイル・制約・決定事項・進捗)は必ず残す**よう要約器へ指示する。汎用要約(書き込み時キュレーション)が抱える「将来に何が要るか分からないまま情報を落とす」ロスを、圧縮という最も頻繁なキュレーション点で回避するのが狙い。タスク外の会話では従来どおり汎用要約にフォールバック。

### 永続記憶(v5.3・hermes-agentの実装パターンをblackboard方式へ翻訳)

`workspace/memory/*.md` を**権威ファイル**として扱う。実行を跨いで知見が残り、全エージェントに共有される。

- **書くのはAI自身**: ボードが静かになったとき発見器が `distill-learnings` を起票し、idleなエージェントがclaimして完了タスクから知見(決定事項/制約/教訓/引き継ぎ)を抽出・追記する。worktree作業→finish_taskでmainへマージされるので、記憶の変更も通常のレビューフローに乗る。処理済みマーカー(`memory/.distilled`)は**エンジンが管理**(AIに書かせない)
- **読むのは全員**: `memory/` の内容はシステムプロンプトへ常時注入。chatメインはラウンド開始ごとに読み直すので、distillの成果が次ラウンドから効く
- **圧縮との権威分離**(hermesの規律): autocompactの要約は memory/ の内容を**複製しない**。記憶は常にシステムプロンプトに生きているので、要約は「記憶に無い会話固有の進捗」に集中させる(二重管理・食い違いの防止)

### 堅牢化+読み取り時ブリーフ合成(v5.4・実走で見つかった課題の対応)

実走(200万トークン消費まで動いたセッション)で判明した3課題の対応と、スポーンのJIT化:

- **予算はラン単位に**: 予算ブレーキの判定をセッション累積→このラン(ループ実行)の消費へ変更。使い切ってもチャットは死なず、次のラウンドから復活する。暴走ラウンドの保険は残る
- **claimedタスクの凍結防止**: 担当者が消える終わり方(予算停止/エラー/idle/継続不能なターン上限)では、請求中タスクが自動でopenへ戻る(`release`。解放メモとともにボード告知)。誰でも再請求できる
- **worktreeの無音破棄を禁止**: 再起動時のworktree初期化は、未コミット変更があるworktreeを**保持**してボードに告知する(前回実行の書きかけが消えない)。クリーンなworktreeは従来どおりfreshに張り直す
- **gather_contextツール(読み取り時キュレーションのspawn適用)**: `source:"board"|"done"|"open"` で生素材(ボード全経過/完了タスク本文/未着手タスク)を読める。スポーンのブリーフは**目標と完了条件だけ**書かせ、素材の引き継ぎは労働者側がclaim時に自分で集める(書き込み時に親が全部詰め込む方式をやめ、読み取り時にタスク適応に合成する)。

### タスクのUI直操作(v5.5・チャット経由管理の解消)

右ペインのタスクパネルから、**チャットに一言も送らずにタスクを管理**できる(blackboardはただのファイルなので、UIが直接触ってもトークンは消えない):

- **投入**: task_id(空欄で自動採番)/role/本文を書いて「タスク投入」。`tasks/open/` に直接置かれ、次にclaimしたエージェントが拾う
- **解放**: 作業中タスクをopenへ戻す(担当者不在のまま凍結している場合の救済。v5.4の自動解放の手動版)
- **中止**: 未着手タスクをdoneへ(削除ではなく履歴に残る)
- **再開**: doneのタスクを再度openへ
- 行クリックでタスク本文を表示。一覧は要約(本文の先頭行)付き。`GET /api/state` に `taskList`、`POST /api/tasks` に `action: create|release|cancel|reopen`

### タスクに文脈(project)を導入(v5.6・別取り組みの混ざりの解消)

タスクファイルに `project:` メタ行を持たせ、**取り組みごとにタスクを分離**できるようにした:

- **作成時に文脈を付ける**: `create_task`ツール/UI投入フォーム/`POST /api/tasks` すべてで `project` を指定可。無ければ「未分類」
- **請求の絞込**: `claim_next_task {project}` はその文脈のタスクだけを対象にする——CUDA案件を進めている間に、前の案件の残タスクを誰かが拾ってしまう混線が起きない。`spawn_agent {project}` なら労働者のブリーフに文脈が渡り、追加請求もその文脈に絞られる
- **素材の絞込**: `gather_context {project}` で done/open の生素材も文脈内だけに限定できる
- **UI**: タスクパネルはprojectごとのグループ表示(未分類は最後)+「すべて/各プロジェクト/未分類」の絞込セレクタ+[移動]ボタンで後から付け替え(`action: "reproject"`)
- 旧形式(role行のみ)のタスクファイルもそのまま読める(移行不要)

### エージェント詳細パネル(v5.7・思考と活動の可視化)

右ペインのエージェントカードを**クリックすると詳細パネルが開き、そのエージェントの思考と活動が時系列で流れる**:

- 💭 思考(reasoningモデルの思考テキスト。`message.reasoning`を取得)/ 💬 発言 / 🔧 ツール実行(コマンドや引数)/ ↳ その結果 / ● 状態変化 / 🗜 圧縮(autocompact・microcompactの発火)
- パネルを開いている間は自動で最下部へ追従(SSEの活動イベントを0.6秒デバウンスで取得)
- ログは1エージェントあたり直近120件を保持(`pushAgentLog`。長文は2000文字で圧縮)

## 設計の核: Gitリポジトリ=blackboard

- `workspace/tasks/open/*.md` に仕事(Issue相当)がファイルで転がる
- エージェントは `claim_next_task` で**自分で仕事を発見して請求**する。請求はファイルのrename(open→claimed)で、同一ボリュームのrenameは原子的なので**二重請求が構造的に起きない**
- **エージェントも `create_task` で仕事を起票できる(v3)**。レビュー指摘の修正作業など、後続の仕事がblackboardに流れる
- 完了は `finish_task`(claimed→done)。成果物はワークスペース内のファイルとして残る
- 報告・指摘・質問は共有ボードへ。**他エージェントの投稿は各ループに「ボード新着」として注入**され、次の判断の材料になる
- **作業の隔離(v3)**: 各エージェントは自分専用のgit worktree(ブランチ `agent/<id>`)で作業する。`finish_task`で**mainへ自動マージ**(直列化済み)。競合したらmainは無傷のまま、エージェント側で`git merge main`→解決→再finishのループへ
- **発見器(discovery)がblackboardに仕事を自動投入する(v2)**:
  - テストプローブ: `discovery.testCommand` を定期実行し、失敗→`fix-test-failures`タスク生成(失敗出力を本文に添付)/復旧→自動解決。ただしimpl等の通常タスクが残る間は未マージ起因の偽失敗防止のため仕事化しない
  - diffプローブ: `git diff reviewed main`に変化→`review-changes`タスク生成(role: review)。レビュー完了で**reviewedタグがmainへ前進**し、次のdiffの起点がリセットされる
  - ラン終了時は「コミット→最終プローブ」の順。テスト失敗だけはopenタスクとして残す(次回ランへの仕事の受け渡し)

## アーキテクチャ

```
src/
├─ engine/loop.js    エージェントループ(model→tools→…、ボード新着の注入、
│                    microcompact/autocompact、idle強制終了、予算ブレーキ)
├─ engine/tools.js   10ツール: claim/finish_task/create_task, read/write/edit_file,
│                    list_files, bash(ゲート通過後Git Bashで実行),
│                    post_to_board, wait_for_board
│                    ※ファイル系は自分のworktree配下に閉じ込め(パス検証)
├─ engine/board.js   共有ボード+待機(waiter)+イベントバス
├─ engine/tasks.js   タスクblackboard(open/claimed/doneのrename管理+イベント発行)
├─ engine/worktree.js worktree作成(毎ランfresh)+mainへの自動マージ(直列化)
├─ engine/discover.js 発見器: テスト失敗→タスク化/復旧→自動解決、
│                    diff(reviewed..main)→レビュータスク化、タグ前進
├─ engine/permissions.js 承認制ゲート(deny即拒否/askはUI承認・タイムアウト拒否)
├─ engine/compact.js コンテキスト管理(ZCode移植: microcompact/autocompact)
├─ engine/usage.js   トークン/コスト台帳(provider usageの実費集計)
├─ engine/exec.js    シェル実行の共用層(WindowsはGit Bash自動検出)
├─ model/openai.js   OpenAI互換アダプタ(GLM等。usage/reasoning_effort対応。依存ゼロ)
├─ runner.js         シナリオ実行器(git blackboard化→worktree→同時走行→最終プローブ)
├─ ui/server.js      localhost UI(node:http+SSE。依存ゼロ。承認ボタン/usage表示込み)
├─ ui/public/        ボード/エージェント状態(トークン・コスト)/タスク/承認要求/ファイル
└─ desktop/main.js   Electron殻(v4): トレイ常駐/ネイティブ通知/単一インスタンス
```

モデルは [OpenRouter](https://openrouter.ai) のGLMで実証(既定 `z-ai/glm-5.3-flash`)。キーは環境変数 `OPENROUTER_API_KEY` か `hive.config.json` の `apiKeyFile`。

## 実証済みのこと(実走)

**v1(2026-09-24)**: wordcount CLIシナリオ。実装→レビュー(実バグ1件を「箇所+原因+修正案+検証済み」で指摘)→修正→独立再検証→総括、全タスクdone。

**v2(2026-09-25)**: counter CLIシナリオ(テストをシードとして先に置き、テストが仕様書)。発見器の全ライフサイクルが実走で乗った:

1. アルファが実装+5/5テスト通過を報告
2. **diffプローブが自動で`review-changes`タスクを生成**→ベータが請求し、動かして検証(複数インスタンス独立性/100万回操作/カプセル化)して「問題なし」→ **レビュー完了でreviewedタグ前進**
3. ガンマが自分でもテスト再実行して総括。改善提案(戻り値契約のテスト追加等)はアルファが自主対応(6/6まで拡張)
4. 追加変更で再生成された2回目の`review-changes`で、ベータが**「差分ゼロ」を確認してクローズ**——diff→レビュー→タグ前進→次のdiffの循環が閉じた

なお初回v2ランでは`node --test tests/`(ディレクトリ指定)がこの環境で失敗するためプローブが偽失敗を出し、fixタスクが生成される事故が起きた。エージェント自身が原因を突き止めており、プローブコマンドをグロブ指定に修正済み。**タスク本文に失敗出力を添付しておくとエージェントが自律で切り分けられる**実例。

**v3(2026-09-25)**: stringutilシナリオ。実装担当2体(アルファ/デルタ)が**各自のworktreeで並列実装**し、それぞれfinish_taskでmainへ自動マージ。その後の循環が全て自動:

1. diffプローブがreview-changesを生成→ベータが査読し、padCenterのwidth検証欠落を指摘
2. ベータが**`create_task`で`fix-pad-width-validation`を自ら起票**→アルファが請求、仕様をテストで固定して修正(6テスト化)→自動マージ
3. ベータが再レビュー(実行確認: XMLHttpRequest→XMLHTTP_REQUEST、日本語、非文字列など境界網羅、10/10 pass)で「問題なし」
4. ガンマ(lead)が自分のworktreeへmainをマージ→全テスト再実行→git logで経緯確認→最終総括
5. 各エージェントは「3回請求できなければ終了」ルールで自発的に退出

単一エージェントには絶対に起きない「レビュー→起票→修正→再レビュー→第三者検証」が、タスクボードとworktreeの上だけで完結した。

### 既知の不完全さ(v3時点)
- エージェントがfinish_taskを忘れたまま次の仕事に着手することがある(この場合もブランチごとマージされるので成果は入るが、タスク状態がclaimedに残る)。複数タスクの同時保有を制限する、または完了忘れ検知が次の改善点
- エージェントの待機サイクル(wait_for_board)がウォールタイムを消費する。runner.timeoutSecは900秒を推奨

## 既知の実装メモ(GLM/OpenRouter特有)

- tool_callsを含むassistantメッセージは `content: null` 不可(空文字へ正規化)
- ツール結果メッセージのcontentは**文字列**でなければならない(配列を渡すと `content[0] must be an object` の400)
- 推論モデルなので思考トークンで `max_tokens` を消費する。空応答が続く場合は上限を上げる
- Windowsではモデルが自然にPOSIXコマンドを書くため、bashツールはGit Bashを自動検出して使う

## ロードマップ

- **v2(完了): 仕事の自動発見**。テスト失敗→タスク自動生成+自動解決、diff→レビュータスク化。承認制ゲート(deny/ask+UI承認フロー)
- **v3(完了): 作業の隔離**。エージェント別git worktree+finish_task時の自動マージ(直列化・競合ループ)+エージェント発タスク起票(create_task)
- **v4(完了): デスクトップ化**。Electron殻(窓/トレイ常駐/ネイティブ通知/単一インスタンス)。サーバーは従来の依存ゼロlocalhost UIのまま、殻だけを追加
- **v5: Discord等の外部表面**。`_projects/discord-agents/` で実装済みのTransportを、このハーネスの出力先として接続(Discordは手段の一つに降格)
- **v6候補**: electron-builderによる配布物化(インストーラ)。シナリオ選択UI、過去ランの履歴ビューア

## 安全設計

- ファイル系ツールはワークスペース配下のみ(パス検証でworkspace外を拒否)
- **bashは承認制ゲートを通る(v2)**: `permissions.deny`パターンは即拒否、`ask`パターンはUIの承認ボタン待ち(既定120秒でタイムアウト拒否)。`--run`無人実行では実質すべてのaskコマンドが拒否される(止まられない経路に承認能力を置かない)
- ループの暴走止め: maxTurns / 全体タイムアウト / 空応答連続の打ち切り
